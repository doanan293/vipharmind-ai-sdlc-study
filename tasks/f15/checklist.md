1. A collection is owned by exactly one of: a user, an organization, or nobody (system); owning by both user and organization is rejected, in the model and by a database constraint.
2. Database constraints allow system collections only as public, user collections as private (not "organization" visibility), and organization collections as organization-visible; conversations get a stored list of chosen collection ids.
3. A user can create a personal collection (key prefixed "u-") or, as owner/editor, an organization collection (key prefixed "o-"); the collection id is derived deterministically from its key; new collections are private and editable by their creator; creation is audited ("collection created", subject = the user). [exact]
4. Plain members cannot create collections in the organization (role error).
5. Visible collections are grouped as "mine", per-organization groups (with the org name), and "public"; system collections appear under public. [exact]
6. Visibility rules: a user sees public collections, their own personal ones, and their organizations' collections (private org collections only for owners/editors; organization-visible ones for all members); superadmins see everything; deleted collections are hidden from everyone.
7. Collections not visible to the caller are reported as "collection not found" (HTTP 404 COLLECTION_NOT_FOUND), not as forbidden; members see shared org collections read-only (cannot edit).
8. Only a superadmin can make a collection public (others get a role error, HTTP 403 FORBIDDEN_ROLE); visibility changes are audited with the title, from/to visibility, and whether the actor acted as superadmin.
9. System collections (e.g. the imported formulary corpus) are read-only for regular users: renaming is refused; the view shows it as system, not editable, with its current release number.
10. Importing a bundle with no owner creates a public system collection.
11. Collection quotas limit how many collections a user or organization can own (default 5 per user over HTTP); exceeding the quota is refused reporting used and limit; a quota endpoint reports collections_used and collections_limit. [exact]
12. Deleting a collection hides it immediately, removes its vector-index points and its current release mapping, and is audited ("collection deleted").
13. Deleting an organization marks its collections deleted; a purge job cleans up deleted collections' points and reports how many it purged (second run purges 0); a CLI command reports "purged N deleted collections". [exact]

16. A new chat conversation stores the collection ids chosen at its first turn and searches only those; follow-up turns use the ids stored on the conversation and ignore ids sent with the request.
17. The search scope (collection -> current release) is resolved per turn from what the user may see, narrowed to the requested ids; collections without a published release, invisible collections and unknown ids are dropped.
18. Retrieval passes an explicit scope to the vector search, which filters to exactly those collections' current releases instead of the configured default; with no scope the default is used.
19. An empty scope searches nothing (no vector query) and returns no results without an error.
20. End to end on Postgres and Qdrant: an org member's search only returns hits from collections they may see (not another user's personal collection); narrowing returns only the chosen collection; after leaving the organization, the next resolved scope is empty and the search returns nothing.

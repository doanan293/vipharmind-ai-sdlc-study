1. Every API error is an RFC 9457 problem document served as application/problem+json with status, a stable UPPER_SNAKE code, type "urn:pharma-agent:problem:<code in kebab-case>" and title = the code humanized (e.g. "Conversation not found"); detail only when there is something specific to say. [exact]
2. Application errors keep their code (e.g. unknown conversation -> 404 CONVERSATION_NOT_FOUND with the id as detail, no errors list).
3. Request validation failures are 422 VALIDATION_ERROR with an "errors" list of {loc, message, type} per field (e.g. ["body","message"] string_too_short; ["path","conversation_id"] string_pattern_mismatch) and no detail. [exact]
4. Routing errors are problems too: unknown path -> 404 NOT_FOUND; wrong method -> 405 METHOD_NOT_ALLOWED keeping the Allow header. [exact]
5. HTTP exceptions keep their codes: auth library codes (REGISTER_USER_ALREADY_EXISTS, REGISTER_INVALID_PASSWORD with its reason as detail, LOGIN_BAD_CREDENTIALS, OAUTH_INVALID_STATE) as 400; 401 -> UNAUTHORIZED keeping WWW-Authenticate: Bearer; 403 -> FORBIDDEN with its detail; the skill upload's invalid-name message appears in "detail". [exact]
6. Service availability errors are 503 problems: SERVICE_STARTING before startup completes, AGENT_UNAVAILABLE for chat without an LLM, SERVICE_NOT_CONFIGURED for skills/feedback without their service and for auth without a database ("the database is not configured"). [exact]
7. Unhandled exceptions become 500 INTERNAL_ERROR without leaking the exception message (no detail). [exact]
8. End to end: unauthenticated chat is a 401 problem (UNAUTHORIZED); duplicate registration is 400 REGISTER_USER_ALREADY_EXISTS; wrong password login is 400 LOGIN_BAD_CREDENTIALS. [exact]
9. Conversation and message list endpoints return pages {"items": [...], "next_cursor": <string or null>}; next_cursor is null on the last page. [exact]
10. Conversations are listed newest activity first with a limit and cursor; paging through yields every conversation exactly once with no gaps even when timestamps tie (ties broken by id).
11. Conversations that have no turns yet are not listed.
12. Messages are paged newest first (each page in chronological order), the cursor fetching older messages; pages have no duplicates or gaps with tied timestamps, and an exact-fit page has no next cursor.
13. Cursors are opaque URL-safe base64 (no padding/"+"/"/") of JSON {"t": UTC ISO timestamp with microseconds, "id": row id}; decoding accepts padding and hyphenated UUIDs, converts other offsets to UTC, and naive timestamps cannot be encoded. [exact]
14. Malformed cursors (bad base64, not JSON, wrong shape, missing/invalid time or id, naive time) are rejected as 422 INVALID_CURSOR (an invalid-input error); an empty cursor means the first page. [exact]
15. limit above 100 or a cursor longer than 512 characters is rejected as 422 VALIDATION_ERROR. [exact]
